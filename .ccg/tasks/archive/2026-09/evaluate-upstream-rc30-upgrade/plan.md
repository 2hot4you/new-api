# 升级至 new-api v1.0.0-rc.30 的实施计划

> 本计划仅在用户确认实施后执行。当前任务不修改业务代码。

## 目标

在不破坏 Molii 现有渠道、计费、API 密钥、模型广场和用量记录的前提下，建立
一个可运行的 rc.30 开发候选，并把适合生产的安全与稳定性修复独立回移到
`develop`。

## 阶段 0：冻结基线与备份

1. 从干净的 `develop` 创建独立 worktree 和 `upgrade/rc30-dev` 分支。
2. 记录当前镜像 digest、Git SHA、环境变量清单和数据库版本。
3. 导出视频模型价格、分组定价、模型元数据和任务插件配置。
4. 对开发 PostgreSQL 克隆库执行完整与 schema-only 备份并演练恢复。
5. 建立 rc.23 → rc.30 的上游补丁清单，给每个提交标记采用、等价、改写或拒绝。

## 阶段 1：整合 rc.24

1. 合并 `v1.0.0-rc.24`，保留 Molii 已有的三个等价补丁。
2. 以测试先行方式移植 HTTP/2 请求体重放和用户敏感操作限流。
3. 运行 relay、渠道测试、兑换码和限流测试。
4. 形成独立提交和审查记录。

## 阶段 2：整合 rc.25

1. 按主题拆分 39 个提交：relay/provider、渠道管理、计费/充值、前端与依赖。
2. 优先移植 Responses 计费、异步退款、充值并发和钱包保护修复。
3. 对 Gateway 字段透传、参数覆盖上下文和渠道测试模式保留上游 API 契约。
4. 对 API 密钥、定价和用量日志冲突保留 Molii UI/数据字段，再补上游行为。
5. 每个主题单独测试、提交和审查。

## 阶段 3：整合 rc.26 与 64 位额度迁移

1. 为 quota 上限、充值、兑换、并发扣减和缓存一致性补充失败测试。
2. 移植钱包范围检查、饱和转换和 64 位 schema 启动检查。
3. 在 PostgreSQL 克隆库把 `users.quota`、`used_quota`、`aff_quota`、
   `aff_history` 改为 `BIGINT`，验证数据、索引和默认值不变。
4. 执行首次启动、重复启动、充值、消费、退款和邀请额度测试。
5. 再整合 vLLM、日志表单和 Bun 更新。

## 阶段 4：rc.27 任务插件架构门

1. 先合入 JS plugin runtime、插件模型、路由、artifact 和管理 UI，但不删除 Molii
   专用 Go adapter。
2. 建立明确的双栈分流：上游内置任务供应商走 JS plugin；StarAI 与 Molii Grok
   走原生 Go adapter。
3. 保持 Task、用量日志、真实用量结算、原始 `channel_id`、临时素材和结果代理
   的 Molii 扩展字段。
4. 为四个 Seedance 渠道、临时素材跨 Key 约束、任务轮询和失败退款编写兼容测试。
5. 导出并重新录入所有视频模型价格，逐模型核对小额真实请求。
6. 只有上述测试全部通过，才允许删除被上游取代的普通内置 Go adapter。

## 阶段 5：整合 rc.28–rc.30

1. 合并 rc.28 代码，加入响应头超时、PostgreSQL simple protocol/JSON、SQLite、
   400 错误和任务模型映射修复。
2. 合并 rc.29 与 rc.30 的最终 GORM 依赖和幂等唯一约束迁移。
3. 不构建或启动 rc.28/rc.29 中间版本；只启动包含 rc.30 修复的最终候选。
4. 在 PostgreSQL 克隆库验证 `tokens.key`、`prefill_groups.name` 迁移首次及二次
   启动均成功。
5. 核对用量统计汇总与原始消费日志、余额、实际结算一致。

## 阶段 6：全链路验收

1. 运行 Go、relaykit、前端类型检查、单测、构建与 i18n 检查。
2. 执行文本、Responses、Claude、Gemini、图片、视频、鉴权和错误码冒烟。
3. 执行 API Key 有序跨分组、StarAI、Molii Grok、GPT Image 2/COS、临时素材、
   用量日志、模型广场与排行榜回归。
4. 对所有计费场景保存请求、预扣、最终用量、倍率、退款和余额对账证据。
5. 开发环境稳定观察 24–48 小时，期间无计费、迁移和轮询异常才进入生产评审。

## 阶段 7：生产发布与回滚

1. 维护窗口开始前再次备份数据库并停止写入。
2. 先运行数据库预检，再部署最终候选；不得用跳过 schema 检查的环境变量绕过。
3. 发布后立即执行小额计费、退款、跨分组和四个 Seedance 渠道核账。
4. 任一阻断指标失败，立即停止流量，按已演练方案回滚应用和数据库。
5. 完成发布后记录实际迁移 SQL、耗时、异常和可复用测试到项目 spec。
