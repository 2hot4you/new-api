# 方案评估

## 方案 A：仅前端分层表达

- 保留 `tokens.auto_groups` 全局有序数组和当前后端选路逻辑。
- 前端按模型厂商展示所选接入点，并根据各分组实际支持的模型生成“有效路由”摘要。
- 不支持请求 `model_id` 的分组只会在本地选路阶段被跳过，不会产生上游请求。
- 改动集中在 API Key 编辑器、翻译和组件测试，难度中等，兼容风险较低。
- 限制：同一批共享分组无法表达不同模型之间互相冲突的优先级。

## 方案 B：模型级路由覆盖

- 保留 `auto_groups` 作为默认路由，新增精确 `model_id -> ordered groups` 覆盖字段。
- 运行时优先使用模型覆盖；未配置覆盖的模型继续使用默认分组顺序。
- 需要修改 Token 持久化与缓存、控制器校验、中间件上下文、渠道选择、模型列表、前端表单与详情展示，并增加数据库、API、权限和重试测试。
- 难度为大型、高风险，但能准确表达不同模型的独立优先级。
- 不建议仅以 provider 作为后端匹配键；provider 是可变元数据，精确 model ID 更适合运行时路由。

## 推荐演进

1. 先实施方案 A，修正用户心智模型并复用现有可靠路由。
2. 在厂商卡片下预留折叠的“高级：模型单独排序”入口。
3. 有真实差异化优先级需求时实施方案 B；只保存偏离默认顺序的模型覆盖，避免每个模型都重复配置。
