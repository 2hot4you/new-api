## Verdict

The exact-two-key shared predicate is the narrow correct design. No architecture/security objection; do not enlarge it to namespaces, all absent keys, a logger change, altered reader admission, or DB cleanup. The following test details must be honored before treating RED/GREEN and full gates as sufficient. They refine the approved plan, not expand source scope.

## Required implementation/test details

1. **Preserve publisher semantics, not just key comparison.** In `model/option.go:598-601`, the existing publisher deletes the two keys from OptionMap and returns success. Replace its key comparison with the shared predicate but preserve deletion/return. The preflight should skip precisely the same two keys before missing/value-change checks (`:327-341`). Do not move them into a generic catalog whitelist, skip other missing options, change validation of server-managed deadline writes, or persist any new value. Deliberately seeding a stale runtime exposure and showing the ordinary publisher still removes it is a useful narrow assertion; do not require the read-only preflight itself to clean stale maps.

2. **Use the real loader contract in direct tests.** `stage=nil` is bootstrap, not options-only (`model/option.go:259-261`, `:322`). A direct no-op assertion must supply `optionsOnly=true` with a genuine captured acknowledged input under the appropriate catalog R boundary, not an invented empty stage or nil/bootstrap stage. Stabilize actual initialization/recovery before taking the baseline; install mutation observers only afterward so legitimate fixture initialization is not counted as a violation. Three repeated calls must preserve full durable state/fingerprint, persisted exact values, absence of excluded runtime keys, and the relevant published snapshot—not merely return nil.

3. **Restore global auth state introduced by the real fixture.** `EnsureLegacyAccessTokenRetireAt` stores to process-global `legacyAccessTokenRetireAt` (`model/user_access_token.go:305-318`). Existing `preserveOrdinaryCatalogRuntime` does not restore that atomic (`model/catalog_sync_runtime_test.go:77-108`). Save and restore its previous value in cleanup; assert the value remains the original seeded deadline across no-op calls. Similarly restore any global request-policy/options state affected by positive controls. No `t.Parallel` for fixtures manipulating global DB/runtime/registry/OptionMap. The initializer must run before mutation counters; its conflict-do-nothing INSERT is still a real executed write even on repeat.

4. **Make concurrency failure causal and cleanup safe.** Hold a genuine old catalog pricing R across the reload. Rendezvous at the actual options loader, release the loader seam, and require recovery to finish successfully **before old R is released**. Checking writer-intent zero only while the loader is paused is insufficient: the buggy version requests W after that point. A fresh pricing read while R remains held must succeed and reach its real callback. Avoid sleeps; use completion/writer-intent/explicit cancellation channels and a watchdog only for leaks. On RED/failure, cancel recovery and release all seams/readers before joining goroutines or fixture cleanup. Do not call fatal assertions from a worker goroutine. Do not claim this local model-level request capture traverses HTTP/auth/billing middleware; its narrower no-W/no-admission-rejection proof is sufficient here.

5. **Keep real-change controls independent of the exclusions.** Both a changed cached effective option and a genuinely uncached effective option must still return the writer sentinel during read-only preflight, with no partial setter execution before the error. For the planned RetryTimes control, stabilize the baseline before modifying persisted input; after proving preflight rejection, run the legitimate W path and verify the actual policy snapshot publishes the requested value. A prefix/case near-match to an excluded key is a useful exactness check if cheap. Existing normalization, price/FX/pending, writer fairness/cancellation tests must remain unchanged and run. Do not turn a deliberately invalid historical fixture into a success or bypass full freshness proof to make this regression pass.

6. **Make three-engine layout compatible with mandatory PG selection.** Put engine at the first subtest level: `TestCatalogPublicationRetiredOptionsKeepNoopReadOnly/postgres/{none,deadline,theme,both}`. The runner appends `/^postgres$` only for `matrix:true` (`deploy/tests/test_catalog_postgres_gate.py:1043`), and rejects any SQLite/MySQL run in mandatory PG mode. Register the three-engine test in a separate or appropriate existing **matrix:true** group; do not simply add it to the current liveness `matrix:false` group. Require all four PostgreSQL children explicitly. The PG-only concurrency test can stay in the nonmatrix liveness group. Retain every previous required name/child and run existing Python contract tests. Local three-engine RED/GREEN must separately exercise actual SQLite/MySQL/PostgreSQL, not PG-only selection misreported as three engines.

## Security and scope disposition

- Retaining the exact stored deadline and runtime auth atomic prevents accidental extension of legacy-token validity; a clean OptionMap does not by itself prove that invariant. `theme.frontend` remains a compatibility row; no deletion or schema change belongs here.
- Excluding these two already-unpublished keys from missing-value comparison does not weaken authentic effective-setting or price/FX changes. Sharing the predicate with the existing delete behavior reduces future disagreement without adding new policy.
- Do not change generic `options failed` categorization in this task: removing the false writer condition addresses the root cause; a separate real effective-setting change can legitimately still emit the sentinel fallback label.
- No fresh feature brainstorming, extra helper module, auth endpoint change, migration, dependency, or production hook is required. The three source/test/gate files named in the plan are sufficient.
- The updated user boundary is decisive: after local normal/race, two independent reviews, and exact new dev CI/CD/runtime acceptance, **main and every production target still remain untouched**. Earlier release authorization does not resume automatically.

No must-change production design issue found. The six details above are acceptance-critical test/implementation constraints; final approval depends on inspecting the actual diff and genuine RED/GREEN/full-gate evidence, not this preimplementation review alone.
