# 模型元数据统一与模型广场厂商标题设计

## 背景

当前模型目录存在两条数据路径：

1. `/models/metadata` 只读取数据库 `models` 与 `vendors` 表。
2. `/pricing` 根据已启用渠道能力生成模型列表，并对数据库中不存在的模型在内存中临时推断厂商、Logo 和部分简介；模型能力又来自后端内置目录，少量默认简介来自前端多语言文案。

这导致模型广场能够显示 DeepSeek、GLM、Kimi、Seedance 和 Grok 等模型，但模型元数据页没有相同记录；默认创建的厂商只有名称和 Logo，厂商介绍为空。

## 目标

- `models` 与 `vendors` 成为模型及厂商资料的权威来源。
- 模型广场不再创建临时模型元数据或临时厂商。
- 当前所有已启用模型在 `/models/metadata` 中都有持久化记录。
- `/pricing` 展示“已启用模型元数据”和“当前可用渠道能力”的交集。
- 模型广场按厂商分段，每段展示厂商 Logo、名称和介绍。
- 保留现有价格、渠道分组、实时性能及 Seedance/Grok 专属展示逻辑。
- 自动补齐不能覆盖管理员已编辑的资料，也不能重新启用被管理员禁用的模型。

## 方案比较

### 方案 A：持久化元数据目录与自动对账（采用）

每个当前可用模型都必须有数据库元数据记录。启动和渠道能力变更后执行幂等对账，创建缺失记录并补齐空字段；模型广场只读取持久化目录。

优点是两个页面天然一致，管理员可以编辑所有资料，后续新增模型也不会依赖前端发版。代价是需要扩展模型字段和增加安全的对账流程。

### 方案 B：完全由管理员手工维护

模型广场只显示管理员提前创建的元数据。实现简单，但新增渠道模型后容易因为漏建资料而在广场消失，不适合当前频繁接入模型的阶段。

### 方案 C：继续使用运行时合成并让管理页展示虚拟记录

无需迁移数据库，但管理页看到的记录不一定可编辑或持久化，仍然存在多份事实来源，因此不采用。

## 权威边界

### 模型元数据负责

- 模型 ID、名称和简介
- 模型图标、标签和所属厂商
- 可声明的端点类型
- 上下文窗口、最大输出、知识截止日期和发布日期
- 输入模态、输出模态和能力标签
- 元数据来源与最后核验日期
- 模型在模型广场是否启用

### 厂商元数据负责

- 厂商名称
- 厂商 Logo
- 厂商介绍
- 厂商状态

### 其他模块继续负责

- 渠道与能力表：模型当前是否真实可用、支持哪些分组和端点
- 计费设置：基础倍率、缓存价格、动态表达式及 Seedance/Grok 专属价格
- 性能模块：延迟、吞吐量和成功率
- API 契约代码：可执行参数校验、请求 JSON、curl 示例和异步轮询规则

`/api/pricing` 是上述数据的只读聚合视图，不是新的元数据存储。

## 数据模型

### Model 扩展字段

保留现有 `description`、`icon`、`tags`、`vendor_id`、`endpoints`、`status`，新增：

- `context_length`
- `max_output_tokens`
- `knowledge_cutoff`
- `release_date`
- `input_modalities`：JSON 数组
- `output_modalities`：JSON 数组
- `capabilities`：JSON 数组
- `metadata_source`
- `metadata_verified_at`

价格币种、倍率和计费表达式不进入 Model 表。

### Vendor

现有 Vendor 已有名称、简介、Logo 和状态，无需新增业务字段。内置厂商资料只作为首次创建或空字段补齐的种子，运行时展示始终读取数据库。

## 内置资料与对账

建立后端单一的内置目录资料注册表，覆盖 Molii 当前精选模型和厂商。现有 `exactMarketplaceCatalogMetadata`、默认模型简介、默认厂商规则和默认厂商图标合并到这一个后端来源，前端不再维护模型事实。

新增幂等对账服务：

1. 读取所有启用渠道能力中的精确模型 ID。
2. 对每个模型查找当前 Model，包括软删除记录。
3. 缺少且没有软删除墓碑时，创建启用的最小 Model 记录。
4. 已知精选模型使用内置资料填充简介、厂商、能力和规格。
5. 未知模型仅创建模型 ID，并按集中厂商规则推断厂商；不编造简介或能力。
6. 已存在模型只补齐空字段，不覆盖管理员填写的内容，不修改状态。
7. 被禁用或软删除的模型不自动恢复，保持管理员对模型广场可见性的控制。
8. 已知厂商不存在时创建；存在时只补齐空 Logo 或空简介。

对账在数据库迁移完成后的启动阶段运行，并在渠道创建、编辑、启停或模型列表变化后再次运行。整个批次使用事务，完成后失效模型定价缓存。`GET /api/pricing` 不再写数据库。

## 模型广场聚合规则

`/api/pricing` 按以下顺序构造结果：

1. 读取状态为启用的 Model 与 Vendor。
2. 读取当前启用渠道能力。
3. 只保留两者的模型 ID 交集。
4. 从 Model/Vendor 返回简介、Logo、厂商和能力资料。
5. 合并实时可用分组、端点和计费配置。
6. 性能指标继续由性能接口按模型 ID 合并。

模型元数据被禁用时，即使渠道仍支持该模型，也不在模型广场显示。渠道全部不可用时，模型元数据仍保留在管理页，但不在模型广场显示。

## 管理页面

`/models/metadata` 继续作为管理员维护入口：

- 列表自动出现当前所有启用模型的持久化记录。
- 表格保持现有模型、厂商、状态和同步信息；扩展规格不全部挤进表格。
- 创建/编辑抽屉增加模型规格、模态、能力、来源和核验日期字段。
- 模态和能力使用多选或标签编辑，不要求管理员手写 JSON。
- 管理员编辑后立即失效模型广场缓存。

## 模型广场厂商分段

每个厂商模型网格上方新增简洁标题区：

- 左侧为现有厂商 Logo。
- 右侧第一行为厂商名称。
- 第二行为厂商介绍，使用弱化文字并限制合理行宽。
- 标题区下方保持现有一至三列模型卡片网格。
- 不使用独立营销卡片、不新增动画，也不改变模型卡片本身。
- 同一厂商跨分页时，在新页面重复显示厂商标题，避免模型失去上下文。
- 未知厂商或介绍为空时只显示可验证的信息，不在前端编造介绍。

厂商标题直接使用 `/api/pricing.vendors` 中的名称、Logo 和简介；前端不维护厂商介绍表。

## 兼容性与迁移

- AutoMigrate 增加 Model 新字段。
- 首次启动对当前启用模型执行幂等对账，存量三个模型记录不被覆盖。
- DeepSeek、GLM、Kimi、Seedance 和 Grok 等当前缺失记录会被创建。
- `minimax-m3`、`qwen3.5-flash` 和 `qwen3.5-plus` 保留当前管理员资料，仅补齐空规格字段。
- 保留模型禁用、软删除和官方同步语义。
- Seedance/Grok 的价格矩阵、API 标签页和专属详情组件不改为通用 LLM 组件。
- 不重新引入 `grok-imagine-video-1.5-preview`。

## 错误处理

- 对账失败记录结构化错误，不覆盖现有元数据；事务回滚避免半批次更新。
- 服务可以继续启动，但模型广场只展示已有持久化元数据与可用能力的安全交集。
- 非法 JSON 数组字段在管理 API 层拒绝保存并返回稳定的字段错误。
- 厂商 Logo 无法解析时沿用现有通用图标回退，不影响模型列表。

## 测试

### 后端

- 对账创建缺失模型和厂商。
- 连续执行两次不产生重复记录。
- 只补空字段，不覆盖管理员简介、Logo、厂商、能力或状态。
- 禁用和软删除模型不被恢复。
- 未知模型只创建最小安全元数据。
- `/api/pricing` 只返回元数据启用且渠道可用的交集。
- `/api/pricing` 请求不再产生数据库写入。
- 模型/厂商编辑后定价缓存失效。

### 前端

- 模型元数据表单可读取和提交新增字段。
- 厂商分段按首次出现顺序稳定展示。
- 每段显示 Logo、名称和简介。
- 同厂商模型保持在同一网格，其他厂商另起一段。
- 简介为空时不显示虚构占位文案。
- 保持现有模型卡、筛选、分页和详情弹窗行为。
