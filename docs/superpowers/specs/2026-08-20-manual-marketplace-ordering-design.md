# 模型广场手动排序设计

日期：2026-08-20
目标分支：`develop`

## 背景

当前 `/pricing` 的默认模型顺序由前端按 `release_date` 倒序计算，供应商列表则缺少可管理的展示顺序。发布日期是模型事实，不应同时承担运营排序职责。管理员需要在模型元数据页和供应商管理中直接调整展示顺序，并让所有访问者看到一致结果。

## 目标与非目标

### 目标

- 模型卡片默认顺序由模型元数据中的持久化顺序控制。
- 供应商筛选项顺序由供应商管理中的持久化顺序控制。
- 管理员通过明确的排序模式拖动记录，并一次性保存或取消。
- 数据更新具备完整性校验、事务原子性和跨数据库兼容性。
- 访客仍可主动选择名称和价格排序。

### 非目标

- 不按供应商对模型卡片重新分组。
- 不修改模型发布日期、发布状态、价格、计费或模型能力数据。
- 不改变首页“最新模型”等确实依赖发布日期的功能。
- 不引入新的拖拽依赖。

## 方案比较

### 方案 A：实体排序字段与原子批量接口（采用）

在 `models` 和 `vendors` 表分别保存展示顺序，管理员提交完整 ID 序列，后端在事务内校验并更新。该方案具有明确的数据归属、可查询性、跨实例一致性和可靠的并发失败语义。

### 方案 B：系统配置保存 JSON ID 数组

不需要实体字段，但删除、恢复和新增记录会产生陈旧 ID，查询时还要额外合并未列出的记录，完整性及可维护性较差。

### 方案 C：每次拖动立即更新单条记录

接口简单，但一次拖动通常影响多条相对位置。多个请求中途失败会形成部分保存，并发操作也更容易互相覆盖。

## 数据模型

`Model` 与 `Vendor` 增加 `DisplayOrder int`，JSON 字段为 `display_order`，数据库字段为 `display_order`。排序值必须为正整数，数值越小越靠前。

- 现有记录在迁移阶段按当前可见顺序一次性固化为连续值。
- 模型现有顺序只在迁移时参考当前发布日期排序结果；迁移完成后 `release_date` 不再影响 `/pricing` 默认顺序。
- 供应商现有顺序在迁移时按当前稳定 ID 顺序固化。
- 新建模型或供应商在其创建事务内取得当前最大值并追加到末尾。
- 删除记录不要求立即压缩序号；下一次完整排序保存会重新写为连续值。

迁移通过 GORM 支持 SQLite、MySQL 和 PostgreSQL。Development 使用的 PostgreSQL 额外提供幂等显式迁移脚本，运行时迁移仍负责兼容未执行显式脚本的环境。回填必须幂等：已有正序号不得在后续启动时被重排，仅对未初始化记录追加序号。

## 管理 API

新增管理员接口：

- `GET /api/models/order`：返回全部未删除模型的轻量排序项。
- `PUT /api/models/order`：提交 `{ "ordered_ids": [1, 2, 3] }`。
- `GET /api/vendors/order`：返回全部未删除供应商的轻量排序项。
- `PUT /api/vendors/order`：提交 `{ "ordered_ids": [1, 2, 3] }`。

写接口在同一数据库事务中完成以下步骤：

1. 拒绝空数组、非正 ID 和重复 ID。
2. 加载并锁定当前全部未删除记录；SQLite 使用项目现有事务兼容路径。
3. 校验提交集合与数据库集合完全一致。
4. 按数组位置写入连续的 `display_order`。
5. 任一更新失败时回滚全部变更。

若保存期间发生并发新增或删除，完整集合校验失败并返回可重试的安全错误，管理员刷新后重新排序。成功提交后调用 `model.RefreshPricing()`，确保公开定价缓存立即失效。

## 管理端交互

### 模型元数据页

页面操作区新增“修改排序”。普通模式保留现有分页、筛选、搜索、批量选择和编辑能力。进入排序模式后：

- 使用专用排序接口加载全部模型。
- 以轻量表格列表显示拖动按钮、模型名称、供应商及状态。
- 隐藏普通筛选、分页和批量操作，避免只排序一个分页或过滤子集。
- 每行首列显示拖动按钮；支持指针拖动、触屏拖动及键盘方向键移动。
- “保存”一次提交完整 ID 序列；“取消”丢弃本地顺序并回到普通列表。
- 保存失败时保留本地顺序和排序模式，显示安全错误并允许重试或取消。

### 供应商管理

供应商管理 Dialog 增加“修改排序”。排序模式复用相同的拖动列表行为，显示 Logo、名称与原始 icon 值。编辑、删除和新增操作在排序模式下停用，避免排序数据集发生本地变化。保存成功后刷新供应商、模型及定价相关查询；取消或关闭 Dialog 清理未保存状态。

前端复用项目已有 `motion/react` 的 `Reorder` 与拖动控制方式，不新增依赖。所有按钮包含可访问名称，并提供独立的键盘上移、下移语义。

## `/pricing` 排序规则

公开定价 DTO 增加模型和供应商的 `display_order`。后端构建定价缓存时按照以下规则输出：

- 模型：`display_order ASC`，再以模型名称作为确定性兜底。
- 供应商：`display_order ASC`，再以供应商名称作为确定性兜底。

前端默认排序值改为“推荐顺序”，直接保持后端顺序。删除“最新发布”选项，保留：

- 推荐顺序
- 名称
- 价格从低到高
- 价格从高到低

筛选只移除不符合条件的模型，不重新计算剩余模型的推荐顺序。模型卡片的全局顺序独立于供应商顺序；供应商顺序仅控制供应商筛选项及其他直接消费供应商列表的展示位置。

## 错误处理与并发

- 排序 API 仅允许管理员访问。
- 请求体设置合理的记录数量上限，拒绝异常超大数组。
- 重复、缺失、未知 ID 以及并发集合变化均返回明确但不暴露数据库细节的业务错误。
- 事务提交前不刷新缓存；事务失败不改变任何公开顺序。
- 前端不做乐观写入公开查询缓存，保存成功后再失效并重新获取。
- 关闭或取消排序时不发送写请求。

## 测试策略

### 后端

- 迁移为现有记录回填稳定顺序，重复执行不改变已有正序号。
- 新建模型和供应商追加到底部。
- 合法完整 ID 集合按提交顺序保存。
- 重复、缺失、未知及超限 ID 被拒绝。
- 更新中途失败时事务整体回滚。
- 并发集合变化不产生部分排序。
- 定价 DTO 按模型顺序返回模型，并按供应商顺序返回供应商。
- SQLite 行为测试为必跑项；数据库逻辑保持 MySQL/PostgreSQL 兼容，PostgreSQL 显式迁移脚本验证可重复执行。

### 前端

- 普通模式不显示可用拖动按钮；点击“修改排序”后显示完整排序列表。
- 指针拖动和键盘上移/下移改变本地顺序。
- 保存发送完整 ID 序列，成功后退出并刷新查询。
- 取消不发送请求并恢复服务端顺序。
- 加载、空数据、失败重试、保存失败保留状态均有覆盖。
- 供应商管理关闭后重新打开不保留旧排序草稿。
- `/pricing` 默认保持后端推荐顺序；名称和价格排序仍可主动选择。
- “最新发布”不再出现在 `/pricing` 排序选项中。

## 发布与兼容性

该改动只增加字段和管理员接口，不修改已有字段语义。旧客户端会忽略新增 JSON 字段。部署后数据库迁移先完成字段创建及回填，再由新版本服务公开排序数据。排序值没有配置时仍使用确定性兜底，避免无序 map 输出造成页面抖动。
